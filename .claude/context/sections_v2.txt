=== SECTION site-tool
file: ~/.claude/context/site-tool.txt
paths: ~/.config/ccorch/**, ~/.local/share/ccorch/**
cmds: (^|[;&|]\s*)site\s
---
```
site list                          sites and whether they are up
site pick <project> [--jobs N --groups G --mem M]   where a job or a batch should go, per-site finish times
site copy <project> <src> <dst> <paths...> [--to D --overwrite]   data between two sites (site to site, never via the laptop)
site env <site> <project>          make the project runnable there: checkout + Python env +
                                   sites/setup.sh (MadGraph, staged datasets, caches...), idempotent.
                                   `site pick` treats a site as deployed only if
                                   `sites/setup.sh --verify` passes there.
site sync <site> <project>         push local commits, fast-forward the site checkout
site submit <site|auto> <project> <job.sh> [--est-gpu-hours H] [--note ..]
site run <site> <project> -- <cmd>   one command on the site's login node, in the checkout,
                                   env activated: sweep generators, sweep_manager submit,
                                   CPU dry-runs. Not for training, not for a shell loop.
site poll [run ...]                refresh states from the schedulers
site logs <run>                    tail the job's log
site fetch <run>                   pull tier-0 results (metrics, small plots, configs) home
site where <run>                   where a run's outputs live (local mirror + remote path)
site runs [--project P] [--site S] the registry (~/.local/share/ccorch/runs.db)
site status <site>                 queue view
```

`site pick` plans a batch so it finishes earliest: per site it measures free GPUs this request fits (host memory,
CPUs), your running and queued jobs, the per-user submit cap, everyone else pending, and what your jobs there really
waited and ran, and prints per site "N sweeps, done in ~X h". A sweep's trials share one filesystem, so a group never
splits. Each named submission (`site submit <site>`, `site run ... sweep_manager.py submit`) spends one unit of the plan
for 60 min. `site pick` treats a site as deployed only if `sites/setup.sh --verify` passes there.

`site submit --hdr=--time=HH:MM:SS` overrides the script's time limit (passed to `sbatch` as a flag).

Inside a job, `source "$_CCORCH_ROOT/sites/activate.sh"` resolves the site and exports `PROJECT_DIR`, `DATA_DIR`,
`SCRATCH`, `SUBMIT_DIR`; Python uses `siteconf` (`siteconf.PROJECT_DIR`, `siteconf.slurm_header(...)`,
`siteconf.resolve(cfg)`). Site-owned directives come from `sites/sites.yaml` + `~/.config/ccorch/sites.toml`.

Where results are: `site fetch` mirrors tier-0 (metrics, summary, config, small plots) to
`~/.local/share/ccorch/artifacts/<project>/<run>/`. Heavy artefacts stay on the site; `site where <run>` prints both
locations. The registry (`~/.local/share/ccorch/runs.db`) records the deployed commit of every run, so a result can
always be tied to code.

=== SECTION ledger
file: ~/.claude/context/ledger.txt
paths: ~/.local/share/ccorch/runs.db
cmds: \bsite\s+(decide|decisions|item|items|supervise|events|ack|digest)\b
---
Enforced where `~/.config/ccorch/projects.toml` has `ledger = true` (FA does).

```
site decide <project> --kind approve|hold|release|forbid|prefer|scope --quote "<the user's exact words>" --covers ...
site decisions [--project P]       the calls in force; also printed into every new or compacted session
site item add <project> <id> --decision D<n> --scope "what runs, how many, how long" --match 'glob,...'
          [--check "<cmd printing {units:{name:{expected,done,active}},alerts:[]}>"] [--notes docs/results.tex]
site items [-v]                    active and held work, with progress
site supervise --project P         the background supervisor (below)
site events [--wait]               open events; `--wait` is the waiter that wakes the main session on the next one
site ack E<n> --note "what was done" [--needs-user WHAT]
site digest --project P            since the user last looked: calls for them, findings, routine handling as
                                   counts, item progress, whether the watch is alive
```

- `site decide` searches the transcripts (mid-turn messages and slash-command arguments included) and refuses a quote
  the user never typed; a hold or release prints the items it covers.
- New work: the user's words, `site decide`, `site item add`, then submit. On the site, sbatch and condor_submit refuse
  without an item; a project's own submitters (FA: `siteconf.work_gate`) refuse anything outside the named items'
  globs or inside a held one.
- The GPU budget lives in the same site-side gate, so every GPU job counts whatever submits it (`site submit`, launch
  scripts, sweep_manager, generators): wall time × GPUs × jobs, summed over the named items' jobs of the last 60 min
  on every site, is refused above 30 GPU-h (10 on Jean Zay) unless the item's recorded estimate (`site item set
  --est-gpu-hours`, from the user's words) covers it. The laptop's submit_guard is the early warning.

The supervisor does the mechanical work, with no model, every 20 min:
- runs the project's `maintain` commands (FA: the CC feeder, the rebalancer over `tp3_`, the disk watch), each active
  item's check (FA: `watchdog.py --units`), and the overrun check of queued runs (with the scheduler's reason);
- sorts every run end into one of three:
  finished clean: COMPLETED, its end marker in the log, no error pattern;
  hit its planned limit: TIMEOUT of a worker whose queue still has tasks and whose wall limit is the one its queue
  states (the worker ends by design and the queue continues);
  broke: anything else (FAILED, OUT_OF_MEMORY, NODE_FAIL, a TIMEOUT that was not a planned limit, an error pattern).
  It acks the first two itself, the note naming the run, its class and the log line that decided it, and opens the
  third as an event for the agent that owns the work;
- resubmits workers only for queues the user approved (the item's decision names the queue and its limits: workers,
  wall time per worker, total hours), within those limits, and only while the queue's layout is current (its spec
  hash equals the recipes' and no replan is pending); otherwise it raises an ALERT;
- collects finished runs (FA: `tools/collect_run.py`) when nothing is off; anything off is an event for the owner;
- never resubmits a failed task;
- raises an ALERT when a batch's progress predicts its end beyond 2× its recorded wall-time target.

Events that reach an agent: RUN (a run that broke), GAP (expected results missing with nothing queued to produce
them), OVERRUN, ALERT, READY (a comparison became possible: analyse it, write it up in the item's notes, commit, show
the user, then ack; it closes only once its write-up is committed). `--needs-user` marks a call only the user can make.

=== SECTION site-facts

paths: sites/**, ~/.config/ccorch/sites.toml
cmds: \bsite\s+\S+\s+(ccin2p3|jeanzay|lxplus)\b, \b(sbatch|scontrol|squeue|condor_\w+|cluster_up)\b

  have internet. It prints a login notice before every command's output; `site` strips it (`strip_banner`: each remote

- Jean Zay: no `--qos`, no `--mem`; compute nodes have NO internet (stage data first); inode quota nearly full (no new
  conda/venv with its own torch).

  user (`cluster_up lxplus`). `site` runs `kinit -R; aklog` before every command there so /afs stays writable. If
  verify still says "AFS token?", the ticket's renew window ended and only the user can relogin
  (`ssh -O exit lxplus && ssh -fN lxplus`); never ask for it while `kinit -R` still works.

=== SECTION working-on-the-plan
file: ~/work/FA/.claude/context/working-on-the-plan.txt
session: main (SessionStart, every source)
tools: Agent, SendMessage
paths: plan/**, tools/plan.py
cmds: tools/plan\.py
---
The plan
- `plan/plan.yaml`, one entry per piece of work: question, objective, the user's authorising words, the mechanism it
  tests and the expected outcome, status (`running`, `waiting_user`, `held`, `done`), owner, hand-off, the wall-time
  targets of its batches, evidence, dead ends and `done_when` (a shell check that passes only when the entry is
  finished). Read an entry with `python3 tools/plan.py show <id>`; write only through `tools/plan.py` (each
  subcommand takes --help). Where hand-off prose in `docs/results.tex` disagrees, the plan wins.

Roles
- The main session talks to the user and directs agents. On every wake (the user's message, an event of an entry, an
  agent's hand-back) it runs `plan next`, which says per entry what moves: `resume <agent>` (SendMessage carrying the
  event), `launch` (a fresh owner from the entry's hand-off), `close <agent>` (context past the threshold), or nothing.
  Routine events never reach it: the supervisor acks them.
- An owner is one background agent per entry in progress (Agent tool, `run_in_background`), its brief rendered by
  `plan brief <entry>` from `plan/step_prompt.txt`, recorded with `plan owner <entry> --agent <id>`. It covers all of
  the entry (analyses, fixes, designs, jobs, write-ups) and is never split into more agents for the same entry.
- While its jobs run, the owner records them, writes its state on the entry and ends its turn (stopped); the next
  event of its entry resumes it with SendMessage. It is never replaced by a fresh agent per event.
- After each hand-back the main session reads the owner's context from its transcript (`tools/agent_context.py
  <agent>`). Near 300k tokens it asks the owner to close: the owner writes its hand-off on the entry (`plan handoff
  <entry> --state --decisions "<what and why>" --ruled-out --running --files`) and ends; a fresh owner starts from
  that hand-off.
- A compaction inside an owner's turn is a finding (its brief or scope was too large): `plan finding <entry>`, and the
  next brief is narrowed.
- Delegated work goes to a fresh agent with a written brief, never a fork.

Briefs
- `plan brief <entry>` fills `plan/step_prompt.txt` with the entry; the main session's addition goes in its narrowing
  slot only. It may narrow the task; it never overrides the capacity and scope rules, and a launch whose brief does is
  refused.

Questions
- Before a question reaches the user, CLAUDE.md and `site decisions --project FA` are searched; only a call none of
  them settles is asked, in the main session's message, and recorded with `plan ask <entry> --ask "<question>"
  --searched "<what was read, why none settles it>" --blocks "<what waits>"`; only what it blocks waits. The answer:
  `plan answer <entry> --kind K --quote "<the user's words>"` records the decision and changes the entry in one step.
- Work held at its design: the "stop at the design" hold [D66]; the larger catalogs' "consult with me on the design"
  [D10].

Designs
- `plan design <entry> --question --prior --measure --check --fixed --control --seeds --outcome`. `--prior` names the
  prior work found in `docs/results.tex`, `plan show` and `site decisions` with its result, or "none found" with the
  terms searched; `--check` says how the measure was shown, on existing data, to move with the tested change. The
  owner launches the design-reviewer subagent itself: on PASS it submits, on FIX it revises once or records a dead end.
  An eval-only re-read of a run under its passed design carries `REREAD=<run id>`.

Jobs
- `site pick FA --jobs N` right before the N submissions; `site submit ... --item <entry>`; record with `plan run
  <entry> <run>` (a sweep: `--sweep <site>:<name>`) and the batch's wall-time target with `plan target <entry> --batch
  <name> --wall <hours> --jobs N`. A batch goes out in parallel: `site sync <site> FA` once, then every launch with
  `NOSYNC=1` (`scripts/launch_cc_only.sh`). New sweep families go into `analysis/transfer/expect_tp3.json` so the
  item's check counts them.

Done
- `plan done <entry> --writeup <commit>` passes only when `done_when` passes, the write-up is committed and the
  entry's commits are inside a passed review. A write-up answering a decision lists each of the user's words that names
  a comparison or a reference, with the result that answers it.

The Stop gate refuses only what the turn can clear: a running entry with something to do and no owner; an open event
of an entry whose owner was neither resumed nor launched; a `waiting_user` question in no message to the user; a
running entry with no approval in force or a held one with no hold; trunk numbers failing the claims check; a figure
without its pair; a context flush wanted; a reply that leaves the user's question unanswered (once per message); a
main-session reply not opening with "Joaquin"; the supervisor down or no armed waiter. A job running, an agent
working, a cluster's state and the user's answer are notes.

=== SECTION fa-generation
file: ~/work/FA/.claude/context/fa-generation.txt
paths: tools/lhe_*.py, scripts/job_lhe_*.sh, recipes/gen_catalog_*.py, mg5_pipeline_final.py, analysis/catalog_v4/data/lhe_*.json
cmds: \blhe_(parts|probe|rates)\b, \bgen_catalog_v\d, \bmg5_pipeline_final\b
---
Before a full queue
1. Probe every process (each energy of an e+e- pool) with a short run: `scripts/job_lhe_probe.sh` running
   `tools/lhe_probe.py run`; it measures the kept fraction after the pool's cuts, wall time per event and disk per
   run; `lhe_probe kept --yields-out` writes `analysis/catalog_v4/data/lhe_probe_yields.json`. `lhe_parts plan`
   refuses a queue with a process the probe file lacks.
2. Generate at the pool's cuts wherever MadGraph's run card can express them (pT, η, ΔR, pair mass), so the kept
   fraction is near 1; only what the card cannot express is cut afterwards, by rejection.
3. Events asked = events needed / measured kept fraction, times at most 1.25 (`KEPT_SAFETY`). A process whose factor
   exceeds 2× is listed by `lhe_parts plan` and fixed (cuts matched, its sampling changed) before the queue goes,
   never absorbed with more runs.
4. Run size from the probe's time per event, so a run fits its wall limit with room; workers = the width
   `site pick FA --jobs N --cpus C --hours H` offers, so the whole queue finishes in one wave; the wall-time target is
   recorded (`plan target`) before submission.
5. MadEvent working directories on node-local disk (`$TMPDIR`), copied back as parts; a saved run's directory is
   deleted, a failed or short one trimmed to its logs [D180, D183].

While it runs
- The supervisor resubmits workers of an approved queue within its limits, and only while its layout is current; it
  acks a worker that hit its planned limit; a failed task goes to the owner, never back in the queue on its own.
- Never replan under live workers: `lhe_parts park Q` first (unclaimed tasks moved aside, workers end with the runs
  they hold), then plan the new queue with `--skip-claimed Q`. A worker started under an older layout returns its task
  (StaleLayout) instead of building a run of the old layout under the new name; `lhe_parts requeue` moves such tasks
  back, nothing deleted.
- Past 2× the target the supervisor raises an ALERT: read where the time goes (yields, run time, queue wait) from
  `lhe_parts yields --queue Q` and the run records before changing anything.

After
- Assembly reads the mixture as training reads it (`lhe_probe mixcheck`) and checks short runs against the reuse pool
  (`lhe_probe runsize`); a pool short at assembly is resized from its measured yield (`resize_short`), never padded
  blindly.

=== SECTION fa-sweeps-and-hpo

Multi-fidelity HPO over training-step budgets, sharing a DyHPO surrogate across
all jobs of a sweep via a lock file on the shared FS.
Key files:
- `generate_sweep.py` — initializes the sweep: samples HP candidates, writes the
  DyHPO state (`dyhpo_state.pkl`), and emits one SLURM script per trial into

- Scaling-sweep generators/analysis: `generate_pretraining_scaling_sweeps.py`,

Submitting a sweep (GPU budget applies): through `sweep_manager.py`, so trials interleave round-robin across sweeps;
never hand-loop `sbatch` over `jobs/*.sh`. The generators render the `#SBATCH` block for the site they run on
(`siteconf.slurm_header`) and submit through `sweep_manager.py`, so they run on that site's login node through
`site run <site> FA -- python sweep/generate_sweep.py --config sweep/<my_config>.yaml`; locally they are dry-runs only.
```bash
# generate; it then prompts to submit (or set cluster.auto_submit / pass --auto-submit)
python sweep/generate_sweep.py --config sweep/<my_config>.yaml
# scaling generators submit all their cells interleaved in one batch:
python sweep/generate_scaling_sweep.py --config sweep/<scaling_config>.yaml
python sweep/generate_pretraining_scaling_sweeps.py --phase both --auto-submit
# submit manually later (interleaves with whatever is already queued):
python sweep/sweep_manager.py submit <sweep_dir>/<sweepA> <sweep_dir>/<sweepB>
```

**Known coupling issue (relevant to job ordering):** jobs share DyHPO state, but
they only inform each other if earlier trials `observe()` before later trials
`suggest()`. If all trials of one sweep start at once (which happens on Jean Zay
when many GPUs free up), they all `suggest()` against an empty/stale surrogate.
When running several sweeps at once, interleave submissions across sweeps
(round-robin) and/or use SLURM priorities so each sweep stays partly serialized.
**Fallback when interleaving can't help (a lone sweep, or abundant GPUs):**
`sweep_manager submit` now defaults to **3 sequential waves** (`--seq-batches 3`)
for a single-sweep submission — the trials are split into 3 groups chained by
SLURM `afterany` dependencies, so wave *k+1* only starts after wave *k* has
`observe()`d and the (single-fidelity) Bayesian optimiser actually has data to fit.
Multi-sweep submissions default to `--seq-batches 1` (rely on interleaving); pass
`--seq-batches N` to force, `1` to disable.
**Chained submission (opt-in, `sweep_manager submit --chain [--capacity N]`).** Holds guided trials until the
preceding trials have observed; use it when free GPUs would start a whole sweep blind. `--weight`/`boost` do not
apply to chained jobs. On HTCondor the chain is the DAG (`cluster.chain_width`). Details: the script's docstring.
**Cross-sweep submitter — `sweep/sweep_manager.py`**. Submits
trials interleaved across sweeps and stamps each job with a SLURM `nice` value =
`round × gap`, where a sweep's `j`-th pending trial has `round = j // weight`.
Same round ⇒ same nice ⇒ runs together (fills GPUs); higher round ⇒ runs later;
`weight>1` ⇒ that sweep advances faster. Uses only user-level `nice` (no operator
rights). Commands: `submit <sweepdir>…`, `rebalance` (re-interleave all pending,
e.g. after adding a sweep), `boost <sweep> --weight N`, `status`, `cancel`.
Add `--dry-run` to preview. Registry: `~/.sweep_manager/registry.json`.
**Rebalancing across sites — `sweep/rebalance.py PREFIX... [--apply] [--allow-jeanzay]`.** `site pick` places a
batch once; this moves trials that have not started from the latest-finishing site to the earliest (by backlog and
achieved rate), deletes nothing (the source is cancelled and marked `MOVED_TO`), and copies a fine-tune parent's
whole run directory if missing. Run by the supervisor over `tp3_`; without `--apply` it prints the plan. Placement
follows `site pick` and this tool, never a hand pick and never a question for me.

HPO search-space rules (harvested from 422 converged sweeps; derivation in `docs/results.tex` § optimization laws):

1. **`training.lr` transfers across width (μP) — never re-sweep it per width.**
   Tune HPs once at the smallest width and reuse for all larger widths (up to a
   5× cut on a width-scaling grid). Re-sweeping lr per width is pure waste.
2. **lr follows an inverted-U in *training length*, peaking at an absolute
   optimizer scale `t* ≈ 3000` steps** (independent of dataset size):
   `lr_c(t) ≈ 1e-2 · min[(t/3000)^+0.5, (t/3000)^-0.55]`. The peak is an optimizer
   timescale (Adam β₂ EMA + warmup + weight EMA), **not** a convergence point — so
   it is not a monotone "more iters ⇒ lower lr": below `t*` the optimum *rises*,
   past `t*` it falls as `t^-0.55`. **The procedure is fixed, not a judgment call:
   evaluate the measured 2D surface `lr*(t,D)` at YOUR `(t,D)` and sweep ±½ decade**
   around it (`[c/3, 3c]`), never a flat 4-decade prior nor the t-only `lr_c(t)`.
   Both axes are set by the run design, so both are known inputs, not uncertainty:
   - **`t`-axis (horizon):** every real run sits past the peak (`t ≫ t*=3000`), so
     `lr*` is on the `t^-0.55`-ish decay — a **longer run takes a lower center**.
   - **`D`-axis (training events summed over the sweep's 8 processes):** measured `lr* ∝ D^{~0.17}`, **saturating**
     (~2.2× from D=700→70k at t=3162, most of it by D~2k). A large-`D` run sits at
     the **high-D asymptote → center ABOVE the D-pooled value**; read it off the
     grid's high-D row at your `t`. Do NOT collapse `D` into "a nudge the window
     absorbs" — that discards a measured axis. (The "is the loss floored?" rule of
     thumb is also dropped — never a measured axis; only `t` and `D` were.)
   - **The (high-`D`, high-`t`) corner is OFF the measured grid** (high-D rows stop
     at `t≈1.8e4`; every large-`t` pooled point comes from small `D≤7k`, which
     over-trains and decays steeply — not representative of a large-`D` run). So
     for a big foundation run (per-proc `D`≈30–100k) the center is an
     **extrapolation of the high-D row's decay**: ~2e-3 @30k, ~1.4e-3 @50k, ~9e-4
     @100k steps. The ±½-decade sweep then both centers the search AND *measures*
     that off-grid corner. Surface + numbers: `analysis/hpo_optima/`
     (`make_fig_2d.py`, `hpo_optima.json`). Template default window `[1e-3, 3e-2]`.
3. **lr is the dominant knob; narrow the rest, don't blindly fix them.** Optima:
   `regularization_lambda ∈ [1e-10, 1e-6]` (cap high at 1e-6; was 9 decades),
   `cosanneal_warmup_frac ∈ [0.05, 0.2]` (median 0.15), `cosanneal_eta_min`
   fix ~1e-8 (or `[1e-10, 1e-7]`, weakest knob), `ema_decay ∈ [0.9, 0.999]`.
   Keep `sampler_alpha_ema ∈ [0.3, 0.95]` (2nd most important). **Drop the exotic
   sampler variants** (`sampler_sig_k`, `sampler_deficit_*`, … |ρ|≈0.1 = noise).
4. **Finetune:** `fine_tune.lr_scale ∈ [0.1, 10]` centered at **1** (best finetune
   lr ≈ pretrain lr), `fine_tune.layer_decay ∈ [0.75, 1.0]`; same reg/warmup rules.
5. **Net effect:** ~10–100× smaller search volume ⇒ halve the trial budget
   (e.g. 300→150 candidates, ~15→~8 obs) at equal resolution, or explore far
   denser at equal budget. Seed new cells from `lr_center(t)`, not a flat prior.
   The `sweep_config*template.yaml` defaults already encode these ranges.
6. **Why HP questions go through DyHPO, single-fidelity** (the rule is in CLAUDE.md) (`fidelity_schedule.t_steps:
   [T]`, one value; the multi-fidelity ladder is unused here) — never a hand-rolled
   grid, whatever the question is called. "Is `clip_grad_norm` the culprit?" and
   "does it work at any `lr`?" are HP searches, not diagnostics. The reason is
   substantive, not stylistic: HPs **interact**, so a 1-D grid at fixed
   everything-else answers only "best `lr` *given those* values", cannot reach a joint
   optimum (one needing `lr` *and* `beta` together), and comes back flat —
   manufacturing a **false** "it doesn't work at any `lr`". Sweep the coupled space.
   Job arrays stay right for **non-HP** ablations (loss type, data tag, warm-start
   checkpoint, ablation flags, seeds).

Sweeps across sites (`sweep/drive.py`):
A sweep no longer has to live on one cluster. `generate_sweep` + `sweep_manager` keep the
DyHPO state in a file that every trial locks on one site's filesystem; `sweep/drive.py`
keeps that state on the laptop and sends stateless trials wherever `site pick` says:
    python sweep/drive.py --config sweep/sweep_config_X.yaml [--config ...] \
        [--n-trials N] [--parallel P] [--mem 8G] [--cpus 4] [--hours 0.5] \
        [--sites ccin2p3 lxplus] [--allow-jeanzay] [--poll 60]
- State and results: `sweeps_local/<sweep_name>/` (dyhpo_state.pkl, driver_state.json,
  results/*.json, summary.txt). Resumable: run the same command again.
- Placement per trial through `site pick` (fitting free GPUs, submit caps, expected waits);
  `--sites` restricts, Jean Zay only with `--allow-jeanzay`.
- Trials run `sweep/trial_job.sh` via `site submit` with `--detached --hp-idx --t-steps --hp k=v`
  (`run_trial.py --detached`): no shared state, result returned as one RESULT_JSON log line.
- Pools: before the first trial on a site the recipe's datasets are checked there and, if
  missing, built by `scripts/prebuild_recipes.sh` as a CPU job on that site (SLURM or HTCondor).

- **Which datasets a run actually trained on: the recipe wins, `data.dataset` lies.**

  the catalog trees whose |M|² is a constant multiple of another's up to a leg relabelling (18 classes,
  `analysis/process_equality/equal_processes.json`: massless flavour relabels, `ee_X = uubar_X` for
  colourless bosons, ...). A held-out process is held out with its whole class.

  shapes train, val and test alike; the shaped pools carry `_smix` in their file names. Never reintroduce a train/eval
  measure split: a finite-sample fit's error follows the training density, so validation estimates the trained risk
  only from the same measure. The uniform-√s window is a dataset convention, not a "physical measure".

  `ee_ttbar_346-1000GeV_amplitudes.npy`. Each row: flat 4-momenta
  (`n_particles*4`) + PDG ids (`n_particles`) + amplitude (last col).

  to COM and applies a random Lorentz transform (data augmentation / locality),
  standardizes momenta, preprocesses amplitudes globally (`amp_trafos: [log,
  standardization]`), concatenates all processes, shuffles (seed 42), and builds
  flat contiguous arrays.
- `dataset.py`:
  - `AmplitudeDataset` — sparse variable-length events backed by a flat
    `(N_particles,4)` array + `offsets`; O(1) `__getitem__`.
  - `collate_variable_length` — concatenates events into a flat batch + `ptr`

- The net: `LearnedPDFrames` framesnet (equivariant local frames via `EquiMLP`)

- Defaults: `num_blocks=8`, `num_heads=8`, `attn_reps="8x0n+2x1n"`,

  (base=2, delta=8); `attn_reps` must stay fixed between base/delta.
### Particle encoding (important design choice)
Two modes, selected by `data.use_PIDs`:
- **`use_PIDs: false` (default, preferred)** — each PDG id maps via a fixed
  global table `GLOBAL_PROPERTY_MATRIX` (in `particle_ids.py`) to a 9-D physical
  property vector (charge, spin, log-mass, T3, B, L, colour charge, Casimir,
  generation), then a learned `Linear(n_features → d_particle_hidden=16)`. The
  table's masses are the **generator's** (u, d, s, c, e, μ massless; b 4.7, t 172.5),
  never PDG values, and the generation column is what tells d from s and u from c.
  `in_channels` depends only on `d_particle_hidden`, **not** on the vocabulary,
  so adding a new particle/feature never forces retraining the transformer.
- **`use_PIDs: true` (legacy)** — one-hot token index from `ParticleTokenizer`.
### Coupling order
`data.amp_orders` is a per-dataset vector `[L_QCD, L_EW, alpha_s_max, alpha_ew_max]`
of the stored target (`mg5_pipeline_final.order_vector`; LO `ee→uū`=`[0,0,0,2]`,
`+g`=`[0,0,1,2]`, mixed four-quark `[0,0,2,2]`, stripped QCD-virt `[1,0,0,2]`; legacy
2-vectors are widened). It's broadcast to every particle as
extra scalar features, so mixing perturbative orders needs **no model change**.
### MuP
Models with `*MuP*` in `_target_` get μP base shapes (`base_shapes.bsh` in the
run dir). Fresh init → `rescale_params=True`; warm start → `False`. See
`base_experiment.init_model`.

- **Per-step host↔device syncs** — `LLOCA_SYNC` env toggle (default `deferred`,
  `blocking` = original for A/B). `deferred` fuses the per-step syncs into one and
  catches NaN via the synced grad-norm (skip-step instead of crash); NaN no longer
  raises. Mechanism and measured gain: `docs/results.tex` § throughput.
- **Dataloading is the per-step bottleneck — keep `num_workers: 2`.** It is the
  default in `config/local/none.yaml`; `nw=4` is no better and `nw=6` oversubscribes
  (`cpus-per-task=8`) and hangs. Profile with `LLOCA_PROFILE_STEP=1` (data-vs-compute
  split at the end of `train()`); bench with `bench_workers_ab.sh` (needs a GPU via
  sbatch). Numbers: `docs/results.tex` § throughput.
- Compute knobs (default on, A/B via config): `training.allow_tf32` (default true) sets `matmul/cudnn.allow_tf32` in
  `_init_backend`: a no-op on V100, faster matmul on A100 at ~1e-3 precision; A/B'd on A100, on and off agree within
  the run-to-run spread, so it stays on. `training.fused_optimizer` (default true, CUDA only) passes `fused=True` to
  Adam/AdamW, through `MuAdam/MuAdamW`.
- **NOT done (deliberately):**
  - L2-reg → decoupled `weight_decay`: would remove a model-sized backward term, but
    the L2 reg is added into the tracked loss (`loss_no_reg`, `val_loss_no_reg`,
    checkpoint selection, HPO objective) and `regularization_lambda` is a tuned sweep
    HP — converting it would silently break continuity with existing sweep results.
  - `torch.compile`: the compute is dominated by the framesnet (torch_geometric
    message passing) and xformers attention, neither of which compiles — heavy graph
    breaks for ~no gain. Also `torch.compile(self.model)` prefixes `state_dict` keys
    with `_orig_mod.`, which would break warm-start/fine-tune reloads. Skipped.
- **Activation-memory knob:** `model.net.checkpoint_blocks` (config, not an env
  toggle; default false) gradient-checkpoints the transformer blocks — large
  activation-memory saving for ~one extra forward of compute. Use when memory-bound
  at large width / batch size.
